# 第二篇 区块链整体架构

> 理解一条链，最有用的方法是**分层拆解**：每层职责是什么、瓶颈在哪、有哪些优化空间。
> 拿到任何区块链平台，都能按这个框架去分析。

---

## 2.1 区块链五（六）层架构

```
        Application Layer   应用层（DApp、钱包、DeFi、NFT）
              |
        Contract Layer      合约层（智能合约、脚本）
              |
        Execution Layer     执行层（VM 执行交易、状态转换）
              |
        Consensus Layer     共识层（决定区块顺序/最终性）
              |
        Network Layer       网络层（P2P、交易/区块广播）
              |
        Storage Layer       存储层（区块、状态、账本持久化）
```

记忆口诀（自底向上）：**存储 → 网络 → 共识 → 执行 → 合约 → 应用**。
不同资料分 5 层或 6 层（有无「合约层」），层数不重要，关键是能说清**每层职责 + 层间关系**。

---

## 2.2 网络层（Network Layer）

职责：节点发现、连接维护、交易与区块的传播。区块链是分布式系统，网络层决定了信息扩散的速度与可靠性。

- **P2P 网络**：无中心服务器，节点对等。
- **Gossip 协议（流言传播）**：节点收到新消息后随机转发给若干邻居，消息像流言一样指数级扩散到全网。优点是鲁棒、无单点。
- **节点发现**：比特币用 DNS seeds + 地址交换；以太坊用 **Kademlia DHT（discv5）**。
- **消息传播优化**：比特币的 `inv/getdata`（先发交易哈希，对方没有再拉取，省带宽）。
- **网络层攻击**：**Eclipse 攻击**（垄断某节点的所有连接，喂假数据）、**Sybil 攻击**（伪造大量身份）。

### 理解：Bitcoin 如何传播一笔交易？

1. 钱包构造并签名交易，发给已连接的若干节点。
2. 节点先做**本地校验**（签名、UTXO 是否存在且未花、金额、脚本），校验通过才接受进 **mempool（内存池）**。
3. 节点向邻居广播 `inv`（交易哈希），邻居没有该交易就用 `getdata` 拉取——**Gossip 扩散**，很快传遍全网。
4. 矿工从 mempool 选交易（通常按费率）打包进候选区块，出块后再广播区块。

> 关键点：「先验证再转发」是防止垃圾交易/DoS 的核心机制；交易在上链前是概率性的，随时可能被替换（RBF）或丢弃。

## 2.3 数据层 / 数据结构（Data Layer）

职责：定义区块和交易的结构、如何链接成不可篡改的账本。

### Bitcoin 区块结构

```
Block
 ├── Block Header
 │     ├── 前一区块哈希 (prev hash)   ← 链接，保证不可篡改
 │     ├── Merkle Root               ← 汇总本块所有交易
 │     ├── 时间戳 / 难度 / nonce      ← PoW 相关
 └── Transactions（交易列表）
```

### Ethereum 区块结构（更复杂，因为有状态）

```
Block
 ├── State Root         ← 全局状态树（所有账户状态）的根
 ├── Transaction Root   ← 本块交易树的根
 ├── Receipt Root       ← 交易回执（含事件日志）树的根
 └── ...（prev hash、gasUsed、timestamp 等）
```

以太坊用的是 **MPT（Merkle Patricia Trie）**：既能像 Merkle Tree 一样做完整性证明，又能像字典树一样高效地按 key（地址）查改状态。三棵树的根都进区块头，任何状态/交易/回执的改动都会导致根变化，因此可验证。

> 为什么以太坊要三个 Root？因为它要能**分别验证**「状态是否正确」「某交易是否在块内」「某事件/日志是否发生」——轻客户端和跨链桥都依赖这些证明。

## 2.4 状态模型（核心章节）

这是区块链设计的**核心分歧点**。

| 模型 | 代表 | 一句话 |
|------|------|--------|
| **UTXO 模型** | Bitcoin | 账本 = 一堆未花费输出；转账即消费+新建 UTXO |
| **Account 模型** | Ethereum | 账本 = 地址→状态的全局映射 |
| **Object 模型** | Aptos / Sui（Move） | 资产是有全局 ID 的「对象」，可独立寻址 |

### 三种模型对比

| 模型 | 优势 | 劣势 |
|------|------|------|
| UTXO | 天然可并行、安全、隐私好、无需 nonce | 表达复杂状态困难，不利于智能合约 |
| Account | 表达力强、开发直观、交易紧凑 | 全局状态竞争，难并行，需 nonce 防重放 |
| Object | 资源安全 + 高并发（无冲突对象可并行） | 生态新、心智模型不同、工具链不成熟 |

### 理解：Object 模型为什么能并行？

Move（Sui）把资产建模成有唯一 ID 的对象。一笔交易在提交前会**声明它要读写哪些对象**。调度器发现两笔交易操作的对象集合不相交，就可以**并行执行**（Sui 的「Owned Object」快速路径甚至不需要全局共识）。这解决了账户模型「所有交易都可能改同一个热点账户」导致必须串行的问题。

> 演进逻辑：UTXO（为安全并行而生）→ Account（为可编程而生）→ Object（想同时要「可编程」和「并行」）。这就是状态模型的演进主线。

## 2.5 执行层 / 存储层

- **执行层**：VM 逐笔执行交易，做**状态转换**：`State + Tx → State'`。要求所有诚实节点执行同一批交易得到同一结果（**确定性**）。这是并行执行、乐观执行、Gas 计量的战场（见第四、五篇）。
- **存储层**：把区块（历史，追加写为主）和状态（可变，频繁随机读写）持久化。常用 **LevelDB / RocksDB（LSM-Tree）**。
  - 痛点：**状态膨胀（State Bloat）**——全局状态越来越大，全节点存储和同步压力剧增。缓解方案：状态过期（State Expiry）、无状态客户端（Stateless Client）、Verkle Tree。

---

## 本篇小结

- 区块链可以自底向上拆成六层：存储 / 网络 / 共识 / 执行 / 合约 / 应用。
- 网络层靠 Gossip 传播，「先验证再转发」防 DoS。
- 数据层用哈希链接 + Merkle 结构实现不可篡改与可验证；以太坊有 State/Tx/Receipt 三个 Root，用于分别验证不同东西。
- 状态模型是核心分歧：UTXO（安全并行）→ Account（可编程）→ Object（两者兼顾），Object 因「预声明读写集」能并行。
- 存储层的长期难题是状态膨胀，业界用状态过期 / Verkle Tree / 无状态客户端来缓解。
